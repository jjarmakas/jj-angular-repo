How it works

Runs as one long-lived process with an internal while ($true) { …; Start-Sleep } loop — not re-launched every second by Task Scheduler (which can't reliably trigger below 1-minute intervals anyway).
Each cycle: lists the JVM log directory, skips the live SystemOut.log/SystemErr.log, and ships anything else (the rotated historical files) to the share via robocopy (restartable /Z, built-in retries — resilient to network blips).
An in-memory name+size cache means unchanged files aren't re-checked against the network share every second — only genuinely new/changed files touch the wire.
A file is only copied once it's been stable (unmodified) for -StabilityWindowMs, so it never grabs a file mid-rotation.
If WAS reuses a historical file name with different content, the old destination copy is archived with a timestamp before being overwritten — nothing is silently lost.
Every cycle is wrapped in try/catch, so a share outage, permission blip, or file-in-use error just logs and retries next second instead of killing the process.
A named Mutex blocks a second instance from starting against the same source path.
Its own diagnostic log at -ScriptLogPath self-rotates at 5MB (5 backups) so it doesn't grow forever.
Running it


.\Copy-WASHistoricalLogs.ps1 -SourcePath 'C:\WebSphere\AppServer\profiles\AppSrv01\logs\server1' -DestinationPath '\\fileshare\WASLogArchive'
If the account running it doesn't already have share write access, create a DPAPI-encrypted credential once as that account (Get-Credential | Export-Clixml C:\WebSphere\LogShipper\share.cred.xml) and pass -CredentialPath.

For production reliability, "run every second" only holds up if something supervises the process, since the script's own loop only protects against errors inside itself, not a crash of PowerShell. Two standard options:

NSSM wrapping powershell.exe -ExecutionPolicy Bypass -File Copy-WASHistoricalLogs.ps1 ... as a real Windows service, with NSSM's auto-restart-on-exit enabled.
A Scheduled Task triggered "At startup" under a service account with "Restart on failure" and "Run whether user is logged on or not" — since the script itself never exits under normal conditions.
